VerifAI — where's the room to improve the model?

model/architecture.py + tokenizer.py + dataset.py · from-scratch bilingual transformer (M4)

1The big one — it can't see evidence

The classifier only reads the claim. Retrieval lives over in app/, but nothing from it enters this model. encode_pair() already builds token_type_ids for [CLS] claim [SEP] evidence [SEP] — the model just ignores them.
⚠️ so it's a plausibility guesser, not a fact-checker. Fix = feed pairs + add a segment embedding. Highest leverage AND most on-thesis.

2Signals that start invisible

TokenEmbedding is scaled by √256 ≈ 16, but the language & learned-position embeddings init at std 0.02.
⚠️ at init, language ≈ 0.1% of the token magnitude — it has to claw its way back during training. Rebalance the scale, OR prepend a language token, OR ablate it and prove it earns its place.

3Pooling & capacity

  • Pool = x[:,0] ([CLS] only) → try masked mean / attention pool — better for small-data from-scratch.
  • FFN hidden = 2×d (line 278); standard is 4×. Bump only if underfitting.
Size is a trap: ~8–12M params already exceed your data.

4The real bottleneck = generalization, not depth

Small labeled set + big model ⇒ overfitting is what caps you. Levers: label smoothing · weight decay · more dropout · augmentation. "improve the architecture" ≠ "make it bigger"

5Off-limits, but be honest about it

Pretrained embeddings/backbone = the biggest raw accuracy lever — but your own rule says no pretrained weights.
✍️ M5 honest move: measure the gap to the XLM-R baseline. That gap IS the finding — don't soften it.
Fix the evidence-blindness (1) first — it's the highest leverage and the most on-thesis. Then spend effort on generalization (2–4), not on a deeper/wider net.
